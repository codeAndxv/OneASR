# OneASR 音频转录优化与工程借鉴策略指南

> **文档定位**：本指南系统性沉淀了 OneASR 在参考业界音视频字幕与语音工程开源实践过程中的架构思考与优化策略，重点阐述长音频切割、Prompt 提示词工程、音频预处理边界、多格式导出规范以及开源协议隔离原则。

---

## 1. 核心架构与背景考量

在音视频全自动转录与本地 ASR 服务的实际生产环境中，单纯调用声学大模型（如 OpenAI Whisper、SenseVoice、Paraformer 等）往往面临诸多现实挑战：
- **长音频截断与显存爆炸 (OOM)**：主流模型单次推断窗口通常在 30 秒左右，长音频直接整段推断极易发生注意力发散、文字截断、重复循环（Hallucination Loop）；
- **上下文断层与专业词误识别**：切片转录时句子前后缺乏语义衔接，行业专有名词或人名缺乏上下文纠错能力；
- **开源协议合规边界**：部分开源转录工具采用 GPL-3.0 协议，商业化或宽松开源项目（如 OneASR 基于 Apache-2.0）严禁复制其源码，必须坚持 **Clean-room（净室工程）** 独立设计。

## 2. 长音频智能分片与 VAD 切片策略

### 2.1 传统固定时长切片的缺陷
- 按固定 30 秒或 60 秒强行切片，高概率将完整单词或语素在中途腰斩，导致切片交界处漏字、吞音或模型严重胡言乱语；
- 空白过长（如背景音乐或长时间静音）送入模型后，极易引发 Whisper 著名的“感谢收看”、“subtitle by...”等幻觉现象。

### 2.2 基于 VAD（语音活动检测）的智能分片
1. **多级静音阈值探测**：
   - 引入轻量级 VAD 算法（如 Silero-VAD 或 WebRTC VAD）；
   - 设置最小静音间隔（如 400ms ~ 800ms）作为天然切分点；
   - 设定单片最小长度（如 3 秒）与最大安全阈值（如 25 秒），防止极端长单句撑爆模型上下文。
2. **前后静音填充与安全边际 (Padding)**：
   - 在每个 VAD 语音块的起始与结束处保留 150ms ~ 200ms 的前置/后置音频缓冲（Buffer Padding），避免首尾音节由于 VAD 阈值触发迟滞被意外削减。
3. **跨片重叠与文字去重 (Overlap Stitching)**：
   - 当遇到语速极快且无自然停顿的超长音频段时，采用 1~2 秒重叠滑动窗口；
   - 基于 Levenshtein 编辑距离或最长公共子序列（LCS）算法消除两片拼接处的重复词汇。

## 3. OpenAI 标准 Prompt 热词注入与上下文接续机制

### 3.1 OpenAI 官方推荐规范解析
OpenAI Audio API (`/v1/audio/transcriptions`) 中提供的 `prompt` 参数，其官方设计初衷为：
1. **引导发音与特定拼写**（如引导模型识别简繁体、专有名词、首字母大写、标点风格）；
2. **前文上下文接续 (Previous Context Prompt)**：将上一音频切片末尾识别出的文本（约最后 200 个字符）作为下一个切片的 `prompt` 输入，使模型保持对说话人语气、语法时态和未说完句式的连贯推断。

### 3.2 热词增强与上下文滚转的工程落地

在 OneASR 中，通过以下策略结合上下文与专用词：

```python
# 核心 Prompt 组装策略示例
def build_chunk_prompt(hotwords: list[str], prev_transcript: str, max_tokens: int = 224) -> str:
    """
    兼顾专有热词与前文连续性的 Prompt 构建策略
    1. 前置热词词表 (如专有名词、人名、项目名)
    2. 后置上一分片的尾部上下文
    """
    prefix = ""
    if hotwords:
        prefix = "以下是可能出现的专有名词或术语：" + "，".join(hotwords) + "。"
    
    # 截取上一片段最后 150 个字符
    tail_context = prev_transcript[-150:] if prev_transcript else ""
    if tail_context:
        prefix += f" 上文接续：{tail_context}"
        
    return prefix[:max_tokens]
```

### 3.3 避坑指南：防止注意力稀释与复读机幻觉
- **严禁无限制灌入巨量热词**：Prompt 长度过大（如超过 250 个字符）会严重稀释声学特征与注意力权重，甚至诱发模型直接复读 Prompt 中的词汇；
- **过滤非法字符与重复循环**：上一片识别如果已出现重复乱码，严禁传入后续片作为上下文，需设立幻觉熔断机制（如检测到单句重复 3 次以上立即重置 `prev_transcript` 为空）。

## 4. 音频预处理与降噪工程考量

### 4.1 传统激进降噪的副作用
在部分音视频处理工具中，往往前置加入谱减法（Spectral Subtraction）或深度降噪模型（如 RNNoise）。但在 ASR 场景中，过度降噪会严重损伤中高频辅音（如齿音、摩擦音 /s/, /f/, /th/），导致识别词错误率（WER）反而显著升高。

### 4.2 OneASR 推荐的轻量预处理边界
1. **统一重采样与声道合并**：
   - 一律转换为 16,000 Hz 采样率、单声道（Mono）、16-bit PCM；
   - 双声道合并时采用归一化均值计算，避免声道抵消；
2. **音量动态标准化 (Normalization)**：
   - 避免微弱声音未激活注意力层，或爆音导致截幅；
   - 采用 EBU R128 或峰值标准化（Peak Normalize 到 -1.0 dBFS）；
3. **降噪决策权移交后端**：
   - 现代端到端 ASR 模型（Whisper-large-v3、SenseVoice 等）自身具备极强的声学背景抗噪能力（加噪训练）；
   - 除非遇到极端持续性低频轰鸣（可开启 80Hz 高通滤波），其余情况优先保留原始音频动态，交由模型端解决。

## 5. 多格式字幕与结构化导出管道

OneASR 支持导出全流派字幕与文本格式，核心处理原则如下：

| 格式 | 应用场景 | 时间戳精度与规范 | 特殊标记 |
| :--- | :--- | :--- | :--- |
| **SRT** | 视频播放器、剪辑软件主流导入 | `00:00:00,000 --> 00:00:00,000` | 换行分句、可带 `[Speaker 1]` 标签 |
| **VTT** | Web 前端播放器 (`<track>`) | `00:00:00.000 --> 00:00:00.000` | 开头声明 `WEBVTT`，支持行内样式 |
| **LRC** | 音乐播放器、歌词/逐句同步 | `[00:00.00]文本内容` | 分秒分秒精简戳 |
| **JSON** | 业务系统二次分析与编辑 | 精确到毫秒浮点数 | 包含单字级别（Word-level）时间戳 |

## 6. 开源合规与 Clean-room 独立设计原则

1. **协议隔离声明**：
   - OneASR 采用宽松友好的 **Apache License 2.0**；
   - 在研究参考业界音视频开源项目与算法策略时，**严格采用 Clean-room 净室流程**：仅吸收宏观工作流设计思路、参数规范与算法逻辑，**严禁复制、粘贴或直接改写任何具有特定开源协议（如 GPL 等）限制的源码行**；
2. **无外部隐式 GPL 二进制强绑定**：
   - 系统所有能力均通过原生标准协议（OpenAI API、标准 FFmpeg CLI、Torch/ONNX 原生模型）解耦，保障商业化友好与企业合规。
